# DongAI 授权与管理端技术设计

状态：设计稿 v2（未实现）　范围：机器码、授权码、邮箱注册、管理端、防倒卖、桌面安装包与证书

已确认的决策：①交付形态是**桌面安装包**，装在用户电脑上，打包证书必须处理好；②视频继续用**用户本机的豆包账号**生成，不经过我们的服务端。

---

## 1. 目标与前提

### 1.1 要解决的问题

软件装在用户自己的电脑上运行，我们要做到：

1. 每台电脑有一个唯一机器码，用户把它发给我们。
2. 我们在管理端据此生成授权码，用户粘贴后才能使用，体验类似 IDEA。
3. 支持邮箱注册。
4. **管理端始终能控制用户能不能用**：能停用、能到期、能换绑，一个授权码拿出去倒卖要么用不了，要么我们能发现并立刻停掉。

不用「账号加密码」作为使用凭证，原因是账号密码可以随便转手；授权必须绑定到具体设备，并且由我们在服务端握有最终决定权。

### 1.2 必须先说清楚的现实

软件跑在用户电脑上，用户拿到的 Python 和前端代码是可以被分析、被改的。**只在本地校验授权码，一定能被破解**：改一行判断、替换公钥、伪造机器码，都能绕过。所以本设计分成三层，不指望任何一层单独守住：

| 层 | 作用 | 能防什么 |
|---|---|---|
| 设备绑定（机器码 + 签名授权码） | 授权码只在被授权的那台机器上有效 | 普通用户把码发给别人 |
| 在线租约（心跳） | 服务端随时能停用，同一授权同时只允许一个在线会话 | 码加机器码伪造工具的批量倒卖、到期后继续用 |
| 关键能力走我们的服务端 | 大模型、出图调用经我们的网关；提示词模板由服务端按租约下发（第 13 节） | 即使本地校验被改掉，也拿不到这些能力。视频因为用用户本机豆包，不在此列 |

第三层是真正的底线。如果核心能力完全在用户本机完成、不经过我们，授权就只是一道可以被绕过的门。视频已确定走用户本机豆包，所以第三层只能靠大模型、出图和提示词模板来做，强度和边界见第 13 节。

### 1.3 非目标

- 不追求防住专业逆向者的本地破解，只保证破解成本高于买正版，并且破解版拿不到服务端能力。
- 本稿不含支付和计费，只留出接口（套餐、功能点、到期时间）。

## 2. 名词

| 名词 | 含义 |
|---|---|
| 机器码 | 客户端根据本机硬件信息算出的指纹字符串，用户复制发给我们 |
| 授权码 | 管理端签发的、绑定一个机器码的签名字符串，用户粘贴到软件里激活 |
| 租约（lease） | 服务端发给客户端的短期令牌，有效期内允许使用，到期前要在线续租 |
| 授权（license） | 管理端里的一条记录：谁、哪台设备、什么套餐、到期时间、状态 |
| 设备（device） | 一个已绑定的机器码 |
| 管理端 | 我们自己用的后台，签发、停用、查看授权 |

## 3. 机器码

### 3.1 采集的信息

不同系统取不同来源，多取几项，避免单点变化就换码：

| 系统 | 主来源 | 辅助来源 |
|---|---|---|
| macOS | `IOPlatformUUID`（`ioreg -rd1 -c IOPlatformExpertDevice`） | 序列号（`IOPlatformSerialNumber`）、主硬盘 UUID |
| Windows | 注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` | 主板序列号、CPU ID、系统盘序列号（WMI） |
| Linux | `/etc/machine-id` | DMI 产品 UUID、系统盘序列号 |

不使用单独的网卡 MAC 地址：容易改、容易随虚拟网卡变化。

### 3.2 生成方式

1. 每个来源各自取值后规范化（去空格、转小写），丢弃明显无效的值（全 0、`Default string`、`To be filled by O.E.M.` 这类占位符）。
2. 每项分别做 `HMAC-SHA256(产品固定盐, 来源名 + 值)`，各取前 8 字节，得到 3 到 4 个分量。
3. 机器码 = 分量按固定顺序拼接后做 Base32，每 5 位一组用短横线分隔，末尾加 2 位校验，例如 `7K4M2-QX9PD-…-A3`。
4. **原始序列号不出本机，也不上传**：服务端只看到哈希。这样也符合隐私要求，需要在隐私政策里写明「收集设备指纹用于授权绑定」。

### 3.3 容错（硬件变更）

授权绑定的是机器码里的分量集合，不是整串字符串：

- 服务端校验时，**分量命中数 ≥ 2（共 3 个）即视为同一台设备**，换一块硬盘或重装系统不会让授权失效。
- 命中数不足视为换了新设备，走换绑流程（第 7.4 节）。
- 虚拟机和克隆盘：克隆出来的机器会得到相同的分量。靠租约的「同一授权同时只允许一个在线会话」处理，见第 6 节。

### 3.4 机器码校验

机器码最后的校验位用来发现用户复制时漏字、多字，管理端录入时也先校验，避免签出一个绑到错码上的授权。

## 4. 授权码

### 4.1 格式

授权码是**服务端私钥签名的数据**，不是随机串，客户端用内置公钥可以离线验证真伪：

```
payload = {
  "v": 1,
  "lid": "lic_8f3a…",          // 授权 ID，管理端可查
  "mc":  [分量1, 分量2, 分量3],  // 绑定的机器码分量（哈希）
  "uid": "usr_…",               // 邮箱账号 ID（可选，第 5 节）
  "plan": "pro",
  "features": ["video", "export_jianying"],
  "iat": 1731500000,            // 签发时间
  "exp": 1763000000,            // 授权到期时间
  "dev_max": 1,                 // 最大设备数，默认 1
  "kid": "k1"                   // 签名密钥编号，用于轮换
}
授权码 = Base32( payload 的紧凑序列化 ) + "." + Base32( Ed25519 签名 )
展示给用户时按 5 位分组、换行，便于复制粘贴
```

- 算法：Ed25519。私钥只放管理端服务器（环境变量或密钥管理服务），**绝不进入客户端安装包和代码仓库**。
- 客户端内置公钥列表（按 `kid`），用于验证授权码和租约。
- 因为 payload 里写了机器码分量，**同一个授权码拿到别的电脑上，分量对不上，直接无效**。

### 4.2 激活步骤

1. 软件首次启动，显示机器码和「复制」按钮，并有邮箱注册入口。
2. 用户把机器码（和注册邮箱）发给我们。
3. 管理员在管理端新建授权，粘贴机器码，选套餐和到期时间，系统签出授权码。
4. 把授权码发给用户，用户粘贴到软件里。
5. 客户端验证：签名有效、机器码分量命中、未过期。通过后立即向服务端「激活」一次，换取租约（第 6 节）。**授权码在服务端记录了首次激活的设备，之后只认这台。**

支持两种发码方式：管理员手工发码（用户要求的方式）；将来也可以由用户在软件里提交机器码，管理员审核后一键签发，减少复制粘贴。

## 5. 邮箱注册

邮箱账号用来识别「谁」，不用来决定「能不能用」。能不能用只看授权和租约。

- 注册：邮箱加密码，发送 6 位验证码验证邮箱（有效 10 分钟，同一邮箱和同一 IP 限频）。邮箱统一转小写，禁用一次性邮箱域名。
- 登录：账号密码只证明身份，**软件能否进入主界面还要求本机已有有效租约**。把账号密码转卖给别人没有用，对方电脑没有授权。
- 一个授权码绑定一个邮箱账号（`uid`）。账号下可以看到自己的设备、授权到期时间、换绑申请入口。
- 忘记密码走邮箱重置。
- 已有的用户名密码账号（现有 `/api/auth/register`、`/api/auth/login`）保留为兼容，新增邮箱字段，后续迁移。

## 6. 在线租约（防倒卖的核心）

### 6.1 为什么需要

只有「机器码 + 授权码」时，有人可以用工具伪造机器码，把同一个授权码用在很多台电脑上，我们完全看不到。租约让服务端始终知道哪个授权在哪里被使用。

### 6.2 租约

激活或续租成功后，服务端返回一个短期令牌（Ed25519 签名）：

```
lease = {
  "lid": "lic_…",
  "mc": [分量…],       // 当前设备
  "sid": "会话 ID",    // 本次在线会话
  "iat": …, "exp": …,  // 默认有效 24 小时
  "st": "active",
  "kid": "k1"
}
```

### 6.3 规则

| 规则 | 说明 |
|---|---|
| 续租 | 客户端联网时每 6 小时续租一次；到期前未续租成功则进入宽限期 |
| 离线宽限 | 租约到期后，允许继续使用 **72 小时**（可按套餐配置），超过后只能看不能用，提示联网 |
| 单会话 | 同一授权同时只允许一个在线会话。第二台设备带着同一授权来续租，服务端拒绝并记录告警；管理端可选择「踢掉旧会话」或「冻结授权」 |
| 吊销 | 管理端点「停用」，授权状态变为 suspended 或 revoked，下一次续租（最长 6 小时内）直接拒绝，租约到期后软件不可用 |
| 到期 | 授权到期后续租返回 expired |
| 时钟回拨 | 客户端把服务端返回的时间和单调时钟存起来；系统时间被改回去，校验失败并要求联网 |

### 6.4 异常检测（自动处理）

续租请求带上机器码分量、客户端版本、IP。服务端记录并检测：

- 同一授权出现机器码分量不一致的两台设备。
- 同一授权在短时间内多个 IP、跨城市或跨国。
- 租约续租频率异常（高频刷）。

命中规则后自动把授权标记为 `flagged`，分三档处理：只告警、踢出会话、冻结授权。管理员在管理端看到列表并人工处理。

## 7. 管理端

管理端是独立的服务和前端，部署在我们自己的服务器上，和客户端软件不是同一个包。

### 7.1 功能

| 模块 | 内容 |
|---|---|
| 授权管理 | 新建（粘贴机器码、选邮箱、套餐、到期时间、设备数上限）、延期、改套餐、停用、恢复、吊销、查看状态和最近在线时间 |
| 设备管理 | 授权下的设备列表（机器码、首次激活时间、最近续租时间、IP）、换绑、踢下线 |
| 用户管理 | 邮箱账号列表、封禁、查看其所有授权 |
| 申请单 | 用户提交的机器码和换绑申请，审核后签发或驳回 |
| 告警 | 异常授权列表（第 6.4 节），一键冻结、一键解除 |
| 审计日志 | 所有管理操作（谁、什么时候、对哪条授权做了什么）不可删改 |
| 看板 | 活跃授权数、今日在线设备、将到期授权、告警数 |

### 7.2 管理员权限

管理端自带管理员账号体系，和用户账号分开，分角色：

- 超级管理员：全部权限，管理其他管理员、轮换签名密钥。
- 运营：签发、延期、停用、换绑、看告警。
- 只读：只看。

管理员登录必须开二次验证（TOTP），所有写操作记审计日志，管理端只允许内网或固定 IP 访问。

### 7.3 状态机

```
pending(待激活) ──激活──> active ──到期──> expired
                          │  ▲
              自动/人工冻结│  │解除
                          ▼  │
                       suspended ──吊销──> revoked（终态）
```

- `pending`：已签发，用户未激活。可设置「X 天内未激活自动作废」。
- `active`：正常使用，续租放行。
- `suspended`：冻结，续租拒绝，可恢复。
- `revoked`：终态，不可恢复，授权码永久无效。
- `expired`：到期，延期后回到 active。

### 7.4 换绑（换电脑）

1. 用户在软件里点「更换设备」，提交新机器码和原因，或联系我们。
2. 管理员审核。同一授权每年换绑次数设上限（如 2 次），超过需人工特批。
3. 审核通过：旧设备从授权里解绑，签发绑定新机器码的新授权码；旧租约在下一次续租时作废。
4. 全程在审计日志留痕。

## 8. 数据模型（MongoDB）

沿用现有 Mongo。管理端和授权服务使用独立的库（如 `dongai_license`），和用户的业务数据库分开，避免业务库泄露带出授权信息。

```
users            { _id, email(唯一), password_hash, email_verified, status,
                   created_at, last_login_at }
licenses         { _id, lid(唯一), uid, plan, features[], dev_max,
                   status, issued_at, expires_at,
                   activated_at, note, created_by }
devices          { _id, lid, mc[], first_seen_at, last_seen_at, last_ip,
                   app_version, bound(bool), unbound_at }
leases           { _id, lid, sid, mc[], issued_at, expires_at, ip, revoked }
activation_reqs  { _id, email, mc[], note, status(待处理/已签发/驳回),
                   created_at, handled_by }
license_events   { _id, lid, type(issued/activated/renewed/suspended/…),
                   detail, ip, at }
alerts           { _id, lid, type, detail, level, handled, at }
admins           { _id, username, password_hash, totp_secret, role, enabled }
audit_logs       { _id, admin_id, action, target, before, after, ip, at }
keys             { kid, public_key, status(active/retired), created_at }
```

索引：`licenses.lid`、`licenses.uid`、`devices.lid`、`leases.(lid, sid)`、`license_events.(lid, at)`。

## 9. 接口

### 9.1 客户端调用（授权服务）

| 接口 | 作用 |
|---|---|
| `POST /license/v1/request` | 提交机器码和邮箱，生成申请单 |
| `POST /license/v1/activate` | 提交授权码和机器码，校验通过后绑定设备并返回租约 |
| `POST /license/v1/renew` | 带当前租约和机器码续租，返回新租约；被冻结、吊销、到期、多会话时返回对应错误码 |
| `GET /license/v1/status` | 查询当前授权状态和到期时间 |
| `POST /license/v1/rebind` | 提交换绑申请 |
| `POST /auth/email/send-code`、`/register`、`/login`、`/reset` | 邮箱注册登录（第 5 节） |

所有请求带客户端版本、机器码分量、时间戳和随机数，并用 HTTPS。续租请求再用租约里的会话 ID 做签名，防止重放。

### 9.2 管理端接口

`POST /admin/licenses`（签发）、`GET /admin/licenses`、`PUT /admin/licenses/{lid}/(extend|suspend|resume|revoke)`、`POST /admin/licenses/{lid}/rebind`、`POST /admin/licenses/{lid}/kick`、`GET /admin/requests`、`GET /admin/alerts`、`GET /admin/audit`、`POST /admin/keys/rotate`。均要管理员登录、角色校验、写审计日志。

### 9.3 错误码

`LICENSE_INVALID`（签名无效）、`LICENSE_MACHINE_MISMATCH`、`LICENSE_EXPIRED`、`LICENSE_SUSPENDED`、`LICENSE_REVOKED`、`LICENSE_SESSION_CONFLICT`、`LEASE_EXPIRED`、`CLOCK_ROLLBACK`。客户端对每种给出明确提示，不泄露内部判断逻辑。

## 10. 客户端实现要点

对应现有项目：

- 后端 `backend/` 新增 `core/license_client.py`（机器码、授权码验证、租约保存、续租线程）和 `api/license.py`（激活页接口）。
- 给 FastAPI 加一个全局依赖：除 `/health`、`/api/license/*` 之外，所有接口都要求当前租约有效，否则返回 403 加错误码。**默认拒绝，出错也拒绝（fail closed）。**
- 前端新增「激活页」：显示机器码、复制按钮、授权码输入框、状态提示；路由守卫在未授权时只允许进入激活页。
- 租约和授权码保存位置：系统钥匙串（macOS Keychain、Windows DPAPI），不存明文文件。
- 打包：用 Nuitka 或 PyArmor 把后端编译和混淆，前端混淆，并在启动时做完整性校验（校验自身关键文件哈希）。这些只能提高破解成本，不能当作保护的全部。

## 11. 交付形态：桌面安装包

### 11.1 组成

```
DongAI 桌面应用
├─ 外壳：Electron（或 Tauri），加载前端页面，管理后端子进程
├─ 前端：现有 Vue 2 构建产物（本地加载，不走网络）
├─ 后端：现有 FastAPI，打成独立可执行文件（sidecar），只监听 127.0.0.1 的随机端口
├─ 数据库：见 11.2
└─ 浏览器：不自带 Chromium，Playwright 使用用户电脑上已安装的 Chrome（现有 channel='chrome' 做法）；没装 Chrome 时引导安装
```

- 外壳建议先选 **Electron**：生态成熟、自动更新和签名流程最完整、前端不用改；代价是安装包大（约 100MB 以上）。Tauri 包小，但 Rust 侧和 sidecar 管理要新学，签名和公证流程也要自己踩坑。**建议 Electron，除非你更看重包体大小。**
- 后端打包：优先 **Nuitka** 编译成原生二进制（同时提高逆向成本、杀毒误报也比 PyInstaller 少）。PyInstaller 作为备选。
- 后端只绑定 `127.0.0.1`，端口随机，并要求外壳启动时传入一次性令牌，防止本机其他程序或网页直接调后端接口。
- 现有代码里写死的配置要改：`STATIC_DIR`、`JWT_SECRET`、Mongo 地址等，全部改为应用数据目录（macOS `~/Library/Application Support/DongAI`，Windows `%APPDATA%\DongAI`）下自动生成，**不能再用仓库里的默认密钥**。

### 11.2 数据库：本地不能要求用户装 Mongo 和 Redis

现在项目依赖 MongoDB（motor）和可选的 Redis，桌面版不能让用户自己装。三个选项：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 随包带 mongod | 安装包里带 mongod，应用启动时拉起，数据放用户目录 | 业务代码几乎不用改 | 包增大约 100MB；mongod 是外部二进制，需要单独签名；杀毒偶尔误报；SSPL 许可证需法务确认随包分发的条款 |
| B 换嵌入式存储 | 抽出数据访问层，换 SQLite 或兼容库 | 包小、稳定、无子进程 | 现有大量 motor 调用要改，工作量最大，需要回归全部流程 |
| C 内存兼容库（如 mongita） | 用纯 Python 的 Mongo 兼容库 | 改动小于 B | 兼容性和并发、性能有风险，需先验证现有查询能否跑通 |

**建议：第一版用 A 尽快出包，同时把数据访问层收口，后续迁到 B。** Redis 在代码里本来就是可选（现在是 disabled），桌面版直接不用。

### 11.3 本机豆包带来的几件事

视频由用户本机的 Playwright 操作用户自己的豆包账号完成，相比之前的账号池方案，这条链路反而简单了很多：

- 不再有「全局共享账号池」和额度分配问题，每个用户用自己的豆包会员额度，**视频生成的成本由用户自己承担**，不是我们的成本。
- 浏览器登录态保存在用户本机的应用数据目录（每台电脑一份），不上传。
- 现有的账号池代码（`doubao_account_pool.py`、`doubao_accounts.json`）桌面版里简化成「当前机器的一个账号」，可以保留多账号，但不再由我们共享。
- **风险要在用户协议里写明**：自动化操作豆包网页不属于官方接口，豆包改版会导致生成失败，账号有被平台限制的风险，由用户自行承担；我们提供适配和更新，但不承诺可用性。
- 豆包页面改版是长期维护成本，需要有「一键更新选择器、不重装也能热更」的通道（可以把选择器和提示词适配配置做成服务端下发，见第 13 节）。

## 12. 安装包签名与证书（必须处理，否则会被系统拦截）

没有签名的安装包，用户会看到「无法验证开发者」「Windows 已保护你的电脑」，杀毒软件还会直接删掉。这是第一次用户体验的门槛，必须在第一次对外发包前做完。

### 12.1 macOS

| 项 | 要求 |
|---|---|
| 开发者账号 | Apple Developer Program（个人或公司，每年 99 美元）。公司账号需要 D-U-N-S 编号，申请要几天到几周，**要提前办** |
| 证书 | Developer ID Application（签 .app 和 .dmg）；如果走 App Store 另需 3rd Party Mac Developer 证书，本方案不走 App Store |
| 签名范围 | **所有嵌套的可执行文件和动态库都要单独签**：后端 sidecar、mongod、Electron 自带的 Helper、Playwright 的 node 驱动、各个 `.dylib` 和 `.so`。漏签一个，公证就会失败 |
| Hardened Runtime | 必须开启。后端是编译后的 Python 和 JIT，需要在 entitlements 里加 `com.apple.security.cs.allow-unsigned-executable-memory` 和 `com.apple.security.cs.disable-library-validation`，只加确实需要的 |
| 公证 | 用 `xcrun notarytool` 提交，通过后用 `stapler` 把票据钉进 .dmg，这样用户离线安装也不报警 |
| 架构 | 同时出 Apple 芯片（arm64）和 Intel（x64）两个包，或做 universal 包 |
| 自动更新 | 更新包同样要签名和公证；更新通道本身用单独的更新签名密钥校验 |

### 12.2 Windows

| 项 | 要求 |
|---|---|
| 证书类型 | **EV 代码签名证书**优先：能直接获得 SmartScreen 信誉，用户第一次安装就不弹蓝色拦截页。OV 证书便宜，但需要积累下载量才能消除警告，初期用户会被吓到 |
| 私钥存放 | 行业规定代码签名私钥必须放在硬件令牌或云端 HSM 里，不能放在文件里。所以要选：硬件 USB Key（要有人在机器前插着签），或云签名服务（DigiCert KeyLocker、SSL.com eSigner、Azure Trusted Signing 等），**CI 里自动签名只能用云签名** |
| 主体 | 证书发给公司主体，需要营业执照、对公账户等验证；国内公司可买国际 CA 的证书，具体哪家受理、几天能下来，要先问 CA，**别等到发版前才办** |
| 签名范围 | 安装器、主程序、后端 sidecar、mongod 等所有 .exe 和 .dll 都签，并带时间戳（`/tr` RFC 3161），证书过期后已签名文件仍然有效 |
| 杀毒误报 | 编译型 Python 和嵌入 Playwright 容易被 Defender、360、火绒、腾讯电脑管家误报。做法：用 Nuitka 而不是 PyInstaller；全部签名；每个版本发布前到微软和国内主要杀软的白名单入口提交样本；不要在安装包里做会触发启发式的行为（自解压后写启动项、注入、混淆过度） |
| 安装器 | NSIS 或 Squirrel/MSI，同样签名；默认按用户安装，不要求管理员权限 |

### 12.3 通用要求

- **证书和私钥不进仓库**，只放 CI 的密钥库或云签名服务的凭据里，签名只能在受控的构建机上跑。
- 构建流水线固定：打包 → 签名 → 公证（Mac）→ 校验（`codesign --verify`、`spctl`、`signtool verify`）→ 计算哈希 → 上传到我们的下载服务器，并发布版本清单。
- 发布前在**干净的虚拟机**上走一遍：全新 macOS、Windows 10 和 11，各装一次，确认无拦截提示。
- 证书到期要有提醒，留足续期时间（EV 证书续期也要重新验证）。
- 授权服务的公钥写进被签名的程序里，被篡改的程序会签名失效，也就起到了防止替换公钥的作用（第 14 节威胁表）。

## 13. 视频走用户本机后的授权强度

### 13.1 坦白的边界

视频生成完全发生在用户电脑上，用的是用户自己的豆包账号，我们看不到也管不到。所以：

- **被破解的客户端仍然能生成视频**，这一块防不住。
- 好消息是：视频的成本在用户自己的豆包账号上，不是我们的成本，被破解损失的只是我们的软件销售收入，不会让我们倒贴钱。

要让授权真的有意义，必须把**对用户有价值、又只在服务端才有的东西**放到服务端。建议三件：

| 放到服务端 | 说明 | 效果 |
|---|---|---|
| 大模型和出图调用走我们的网关 | 剧本、分镜、提示词、三视图等所用的模型由我们统一采购，用户不再自己填 Key；网关校验租约和授权功能点，并按授权记录用量 | 破解版用不了这些能力；同时是后续计费的基础 |
| 提示词模板和拼装规则按租约下发 | 现在 `core/prompts/*.json`、`video_prompt.py` 里的拼装逻辑是产品核心价值。把模板内容（system.json、constraints.json）和拼装用的配置放服务端，客户端拿租约换取加密的模板包，内存里使用，不落盘明文 | 没有有效租约就没有好用的提示词，破解版出来的视频质量大打折扣 |
| 豆包页面适配配置下发 | 选择器、确认流程参数这类经常随豆包改版而变的配置从服务端下发 | 破解版版本一旧就会失效，需要持续更新才能用；正版用户自动保持可用 |

后两项的取舍：提示词在内存里仍然可以被有经验的人导出，不是绝对安全，但能把「拷一份代码就能用」变成「要持续对抗」，符合防倒卖的目标。

### 13.2 对授权的影响

- 租约规则（第 6 节）不变，仍然是单会话、可吊销、有宽限期。
- 宽限期内（断网 72 小时）已经下发的模板包在本地加密缓存，保证短暂离线可用；缓存绑定租约，到期即废。
- 完全不联网的用户（保密环境）不在本方案范围内，需要另做离线版并接受更弱的控制力。

## 14. 威胁与对策

| 威胁 | 对策 | 残余风险 |
|---|---|---|
| 把授权码发给别人 | 码绑定机器码分量，换电脑无效 | 无 |
| 授权码加伪造机器码的工具倒卖 | 租约单会话、IP 和设备异常检测、告警后自动冻结 | 对方只要错开时间使用就难以发现，靠网关用量异常补强 |
| 改本地代码跳过校验 | 编译混淆、完整性校验；核心能力走网关 | 本地界面可被绕过，但拿不到服务端能力 |
| 替换内置公钥，自签授权码 | 完整性校验加公钥多处冗余；网关只认服务端私钥签的租约 | 能过本地，过不了网关 |
| 改系统时间延长授权 | 单调时钟加服务端时间校验；租约到期后必须联网 | 全程离线的用户在宽限期内无法发现 |
| 抓包重放租约 | 租约绑设备和会话，续租请求带随机数加签名 | 无 |
| 私钥泄露 | 私钥只在管理端服务器，支持 `kid` 轮换；泄露后发布新版本换公钥，旧密钥签的授权作废 | 老版本客户端需强制升级 |
| 管理员账号被盗 | TOTP、IP 白名单、审计日志、操作可追溯 | 无 |
| 虚拟机克隆 | 同授权多会话冲突检测 | 无 |
| 破解版客户端自己调用豆包生成视频 | 视频走用户本机无法阻止；对策是模板、模型能力放服务端，豆包适配配置持续下发（第 13 节） | 破解版仍可生成视频，但质量和可用性取决于是否拿得到下发内容 |
| 安装包被篡改后重新分发 | 全平台代码签名，被改动后签名失效；程序启动自校验；官网提供哈希 | 用户若无视警告强行安装，我们管不到 |

## 16. 待确认的问题

已确认：交付形态为桌面安装包；视频继续使用用户本机豆包账号。

仍需要你定的：

1. **大模型和出图是否改为由我们统一采购、走网关**（第 13 节第一项）。这决定我们有没有可管控的服务端能力，也是盈利的主要抓手。不做的话，防倒卖只剩设备绑定和租约，强度较低。
2. **提示词模板是否下发**（第 13 节第二项）。会增加一套加密下发和缓存的工作量，但是防止被整包拷走的有效手段。
3. **本地数据库选 A（随包带 mongod）还是 B（换嵌入式存储）**（第 11.2 节）。建议第一版 A。
4. **桌面外壳选 Electron 还是 Tauri**（第 11.1 节）。建议 Electron。
5. **平台范围**：先出 macOS、Windows 还是两个都出；是否需要 Intel Mac。证书和公证的工作量按平台计算。
6. **公司主体**：Apple 开发者账号和 Windows EV 证书都需要公司主体和对公验证，用哪个主体，谁来办，需要提前启动，因为周期不由我们控制。
7. **一个授权几台设备**：默认 1 台，是否提供 2 台套餐。
8. **离线宽限期**：默认 72 小时，是否有全程离线的客户。
9. **授权形态**：买断、年付、月付；到期后是只读还是完全不可用。
10. **邮件发送服务**：阿里云邮件推送或腾讯企业邮，发信域名和 SPF、DKIM 配置。
11. **管理端部署位置和可用性**：放哪台服务器、域名、是否仅内网；授权服务宕机时客户端靠宽限期继续使用。
